## What this project is

`V8-FILTER-DERIVATION` is a disciplined research effort to find and prove
out an entry filter + exit rule for a Solana memecoin (pump.fun) social-
alert trading bot. The methodology has been deliberately strict throughout,
enforced across many prior sessions, not just this one:

- **Pre-registered candidates only.** Entry candidates (BASELINE-0, V8-P0,
  V8-P1, V8-P3) and exit candidates (E0, E1, E2, E3) are frozen, hashed
  registries (`research/v8_candidate_registry.py`,
  `research/v8_exit_registry.py`). No candidate is chosen or tuned by
  looking at outcomes. Any change to a frozen registry requires an
  explicit, visible "experiment vN" bump (count + hash both change), never
  a silent in-place edit.
- **Holdout is locked and has never been opened.** All readiness/data
  work only ever reads train+validation-level counts. Reading holdout
  row *counts* (how many rows fall in that bucket) is fine; reading their
  *outcome values* (`pct_change_peak`) is never done and is structurally
  checked for in tests.
- **`LIVE_TRADING=false`** in the VPS `.env` throughout. Untouched. This
  entire effort is research/paper-only until the user explicitly says
  go-live.
- **Never invent a threshold and present it as data-derived.** Every
  numeric floor in this system (`MIN_ENTRY_N=100`, `MIN_PATH_COVERAGE_
  PCT=50%`, etc.) has a documented provenance — either a cited external
  convention or a real, live-computed statistic — never a guess dressed
  up as derivation. This has been violated once before (P2-3, an assumed
  `channel_velocity_5m<=5` threshold that had to be caught and fixed) and
  the project has been careful never to repeat it since.

  `admitted_with_tick_n` / `admitted_with_valid_usable_path_n` — the

produced)`. Also fixed a real units-mismatch bug: execution-proxy
coverage's `eligible_n` was an event count while `observed_n` was a mint
count — not commensurate whenever a mint has more than one alert. Both
sides are now consistently mint-level. Added IPW effective sample size
(Kish ESS) over the sampler's recorded inclusion probabilities. Absolute
evidence thresholds (`MIN_PATH_N=100`, `MIN_PATH_COVERAGE_PCT=50%`,
`EXECUTION_PROXY_MIN_N=100`, `EXECUTION_PROXY_MIN_COVERAGE_PCT=50%`) were
**not changed** — only what population they're evaluated against.

### 4. `path_stats.py --valid-only` (commits `7d2e319`, `333dbfb`)
A second real gap: `research/v8_exit_registry.py`'s own audit had

Re-ran the previously-blocked "reversal then bounce" analysis on the
clean corpus (374 tokens after excluding 3,847 corrupted ones): 257/374
(69%) showed a qualifying ≥10% pullback-then-reversal. Positive median
bounce afterward in the $10-100k mcap bands (+14% to +20%). The <$10k
band's number (+19,848% median) was flagged as thin-liquidity noise, not
real signal — a handful of near-zero-liquidity tokens where one trade
can move price 5x, not something tradeable.

### 5. E3 exit candidate added — "EXPERIMENT V2" (commit `9fd7a71`)
User asked for the reversal/timing data to actually inform exit-rule
design (stop-loss / timeout), not just sit in a report. The exit
registry's own frozen-registry mechanism exists exactly for this: an
explicit, visible "experiment v2," not a silent edit.

Derivation: `_shakeout_depth_for_target`/`_time_to_target_minutes`
(newly extracted, pure, tested) run against every clean token that ever

distortion in this one).

hard_stop/trail_tiers verbatim, only `time_stop_min` changed to 7**
(vs 90/45/120 for E0/E1/E2) — a large, deliberate, explicitly-flagged
departure, not a quiet tweak. `EXIT_REGISTRY_VERSION` 1→2, candidate
count 3→4, hash recomputed, `ENGINE_READY` reconfirmed True.

**E3 has not been evaluated against E0/E1/E2 in any way.** It's a new,
equally-unproven candidate now sitting in the same registry, waiting for

## THE open problem — read this carefully

**Path yield (`admitted_path_yield_pct`) is trending in the wrong
direction as the sample grows, not converging toward the 50% floor.**

| | 2026-08-25 | 2026-08-29 |
|---|---|---|
| path_admitted_n | 41 | 408 |
| admitted_with_valid_usable_path_n | 21 | 65 |
| **admitted_path_yield_pct** | 51.22% (briefly cleared it) | **15.93%** |

This is not obviously a bug — it looks like it may be a real, structural
ceiling: **most alerted pump.fun tokens genuinely don't get enough real
trades in the ~15-60min tracking window to produce usable price data.**
That's a true fact about this market (most memecoins die with almost no
volume), not a pipeline defect. If the true steady-state yield sits at
~16% rather than trending toward 50%, `SELECTION_DATA_READY` may not
resolve just by waiting — it may need either (a) much more raw volume so
the absolute-100 floor clears even at a low percentage (this floor
doesn't care about %, only count — currently 65/100, closer than the
percentage suggests), or (b) a design conversation about whether 50% is
the right floor given the market's real thinness, or (c) something that
changes which tokens get admitted/tracked in the first place.

**Open, unanswered, explicitly-flagged-as-not-yet-investigated
question:** does anything already knowable at alert time (before
buying) — `channel_velocity_5m`, `vsol_at_signal`, `progress_at_signal`
— correlate with whether a token later produces usable path data? If
yes, that's fair game for a new, disciplined entry-candidate condition
(predictable in advance = legitimate to filter on). If no, this "waste"
is closer to genuinely unavoidable given what's observable at signal
time. **This has been discussed with the user and offered as a next
step but not yet executed as of this report.**

**Explicitly rejected framing, worth remembering if it comes up again:**
"just build the filter on the tokens that got usable data" is a
survivorship-bias trap — a token having tradeable-enough activity
*afterward* is not knowable *before* buying it, so restricting the
backtest population to only those tokens tests a rosier, curated
population than what a live bot actually faces. This was explained in
detail to the user and they understood/accepted it — don't need to
re-litigate if it resurfaces, but do re-explain if a future session
proposes it without this context.
